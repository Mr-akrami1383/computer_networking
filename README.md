# پروژه پراکسی هوشمند دی‌ان‌اس (Smart DNS Proxy)

## ۱. معرفی پروژه

هدف این پروژه، طراحی و پیاده‌سازی یک پراکسی هوشمند دی‌ان‌اس با زبان برنامه‌نویسی پایتون است.

این برنامه نام دامنه را از ورودی کنسول دریافت می‌کند و پس از اعتبارسنجی و نرمال‌سازی، آن را با دو فهرست محلی تبلیغات و دامنه‌های تحریم‌شده بررسی می‌کند. در صورتی که دامنه در هیچ‌کدام از این فهرست‌ها وجود نداشته باشد، درخواست از طریق پروتکل UDP به سرور بالادستی (Upstream) ارسال می‌شود.

همچنین برای افزایش سرعت پاسخ‌گویی، قابلیت ذخیره‌سازی موقت اطلاعات دامنه‌ها (Cache) در برنامه پیاده‌سازی شده است.

این پروژه علاوه بر قابلیت‌های اصلی، شامل امکانات امتیازی مانند نمایش آمار درخواست‌ها، بارگذاری مجدد فهرست‌ها، نمایش محتوای کش، ثبت گزارش درخواست‌ها، محدودیت ظرفیت کش و اتصال به سرور واقعی دی‌ان‌اس است.

## ۲. قابلیت‌های پروژه

### ۲-۱. قابلیت‌های اصلی

- دریافت نام دامنه از ورودی کنسول
- بررسی معتبر بودن نام دامنه واردشده
- مدیریت ورودی‌های خالی و نامعتبر
- تبدیل حروف بزرگ نام دامنه به حروف کوچک
- حذف نقطه پایانی نام دامنه
- بررسی دامنه در فهرست تبلیغات و فهرست تحریم‌ها
- اولویت دادن به فهرست تبلیغات در صورت وجود دامنه در هر دو فهرست
- ارسال درخواست دامنه‌های عادی به سرور Upstream از طریق UDP
- دریافت نشانی IP و مقدار TTL از سرور Upstream
- مدیریت خطاها و پایان زمان انتظار پاسخ سرور
- ذخیره پاسخ‌های موفق در کش محلی
- محاسبه زمان باقی‌مانده TTL
- حذف رکوردهای منقضی‌شده از کش
- نمایش نتیجه با قالب مشخص شامل Domain، Source، Status، IP و TTL

### ۲-۲. قابلیت‌های امتیازی

| قابلیت | توضیحات |
|---|---|
| B1 - آمار درخواست‌ها | نمایش تعداد درخواست‌ها و آمار پردازش آن‌ها با دستور `stats` |
| B2 - بارگذاری مجدد فهرست‌ها | خواندن مجدد فهرست تبلیغات و تحریم‌ها بدون راه‌اندازی مجدد برنامه با دستور `reload` |
| B3 - نمایش کش | نمایش اطلاعات دامنه‌های ذخیره‌شده در کش با دستور `cache` |
| B4 - ثبت گزارش | ثبت درخواست‌های پردازش‌شده در فایل `log.txt` |
| B5 - محدودیت ظرفیت کش | تعیین حداکثر تعداد رکوردهای کش با استفاده از `cache_max_entries` و حذف قدیمی‌ترین رکورد هنگام پر شدن ظرفیت |
| B6 - اتصال به دی‌ان‌اس واقعی | امکان دریافت پاسخ از سرورهای واقعی DNS مانند `8.8.8.8` و `1.1.1.1` |

## ۳. پیش‌نیازها و وابستگی‌ها

برای اجرای پروژه، موارد زیر مورد نیاز هستند:

- نصب زبان برنامه‌نویسی Python نسخه 3.9 یا بالاتر
- دسترسی به ترمینال یا خط فرمان سیستم‌عامل
- امکان استفاده از ارتباط شبکه‌ای UDP
- نصب کتابخانه `dnspython` برای استفاده از قابلیت امتیازی B6

برای نصب کتابخانه مورد نیاز قابلیت B6، دستور زیر را اجرا کنید:

```bash
pip install dnspython
```

در حالت شبیه‌سازی‌شده، ارتباط بین پراکسی و سرور Upstream با استفاده از سوکت‌های UDP و بدون نیاز به کتابخانه‌های آماده DNS انجام می‌شود.

## ۵. تنظیمات پروژه

تنظیمات برنامه در فایل `config.txt` قرار دارند.

نمونه محتوای این فایل:

```ini
upstream_ip=127.0.0.1
upstream_port=5354
upstream_timeout_sec=2

sinkhole_ip=0.0.0.0
proxy_ip=192.0.2.10
local_ttl=60

ad_list_file=ad_list.txt
sanction_list_file=sanction_list.txt

cache_enabled=true
log_enabled=true
log_file=log.txt

real_dns_enabled=false
dns_server_ip=8.8.8.8
```

### توضیح پارامترهای تنظیمات

| پارامتر | توضیحات |
|---|---|
| `upstream_ip` | نشانی IP سرور Upstream |
| `upstream_port` | شماره پورت UDP سرور Upstream |
| `upstream_timeout_sec` | حداکثر زمان انتظار برای دریافت پاسخ |
| `sinkhole_ip` | نشانی IP بازگردانده‌شده برای دامنه‌های تبلیغاتی |
| `proxy_ip` | نشانی IP بازگردانده‌شده برای دامنه‌های تحریم‌شده |
| `local_ttl` | مقدار TTL برای پاسخ‌های محلی |
| `ad_list_file` | نام فایل فهرست تبلیغات |
| `sanction_list_file` | نام فایل فهرست تحریم‌ها |
| `cache_enabled` | فعال یا غیرفعال کردن کش |
| `log_enabled` | فعال یا غیرفعال کردن ثبت گزارش |
| `log_file` | نام فایل ثبت گزارش‌ها |
| `real_dns_enabled` | تعیین حالت استفاده از DNS واقعی یا شبیه‌سازی‌شده |
| `dns_server_ip` | نشانی IP سرور DNS مورد استفاده در حالت واقعی |
| `cache_max_entries` | حداکثر تعداد رکوردهای مجاز در کش |

برای فعال‌سازی محدودیت ظرفیت کش، می‌توان پارامتر زیر را به فایل تنظیمات اضافه کرد:

```ini
cache_max_entries=2
```

در این مثال، حداکثر دو رکورد در کش ذخیره می‌شود.

## ۶. قالب فایل‌های فهرست دامنه‌ها

دو فایل `ad_list.txt` و `sanction_list.txt` برای نگهداری دامنه‌های تبلیغاتی و تحریم‌شده استفاده می‌شوند.

در هر خط از این فایل‌ها، یک نام دامنه قرار می‌گیرد.

### ۶-۱. فایل ad_list.txt

نمونه:

```text
ads.example.com
doubleclick.net
advertising.example.org
both.example.com
```

### ۶-۲. فایل sanction_list.txt

نمونه:

```text
blocked.example.net
restricted.example.org
service.example.org
```

نکات مربوط به فهرست‌ها:

- هر خط شامل یک نام دامنه است.
- خطوط خالی نادیده گرفته می‌شوند.
- خطوطی که با علامت `#` شروع می‌شوند، به‌عنوان توضیح در نظر گرفته شده و پردازش نمی‌شوند.
- دامنه‌های نامعتبر هنگام بارگذاری فهرست‌ها شناسایی می‌شوند.
- دامنه‌های زیرمجموعه یک دامنه ثبت‌شده نیز با آن تطبیق داده می‌شوند.

برای مثال، اگر `example.com` در فهرست قرار داشته باشد، دامنه `shop.example.com` نیز با آن تطبیق داده می‌شود.

### ۶-۳. اولویت فهرست‌ها

در صورتی که یک دامنه هم‌زمان در هر دو فهرست تبلیغات و تحریم‌ها وجود داشته باشد، فهرست تبلیغات اولویت دارد.

بنابراین ترتیب بررسی دامنه‌ها به شکل زیر است:

۱. بررسی فهرست تبلیغات

۲. بررسی فهرست تحریم‌ها

۳. ارسال درخواست به سرور Upstream

## ۷. نحوه اجرای پروژه

این پروژه از دو برنامه مستقل تشکیل شده است:

۱. شبیه‌ساز سرور Upstream

۲. برنامه اصلی DNS Proxy

برای اجرای صحیح پروژه، ابتدا باید سرور Upstream اجرا شود و سپس برنامه اصلی پراکسی راه‌اندازی گردد.

### مرحله اول: اجرای سرور Upstream

ابتدا یک ترمینال باز کرده و وارد پوشه اصلی پروژه شوید.

سپس دستور زیر را اجرا کنید:

```bash
python upstream.py
```

سرور Upstream با استفاده از مقادیر تعیین‌شده در فایل `config.txt` روی IP و پورت مشخص‌شده منتظر دریافت درخواست‌ها می‌ماند.

با تنظیمات نمونه، سرور روی نشانی زیر فعالیت می‌کند:

```text
127.0.0.1:5354
```

پس از اجرای سرور، ترمینال اول باید باز بماند.

### مرحله دوم: اجرای برنامه اصلی پراکسی

یک ترمینال جدید باز کرده و مجدداً وارد پوشه اصلی پروژه شوید.

سپس دستور زیر را اجرا کنید:

```bash
python main.py
```

در این مرحله برنامه اصلی اجرا شده و آماده دریافت نام دامنه از کاربر است.

### مرحله سوم: وارد کردن دامنه

پس از اجرای برنامه، نام دامنه مورد نظر را در کنسول وارد کنید.

برای مثال:

```text
Enter domain (or exit): normal.example.net
```

برنامه دامنه را بررسی کرده و نتیجه را با قالب مشخص‌شده نمایش می‌دهد.

### مرحله چهارم: خروج از برنامه

برای پایان دادن به اجرای برنامه اصلی، دستور زیر را وارد کنید:

```text
exit
```

## ۸. دستورات قابل استفاده در کنسول

برنامه اصلی از چند دستور مدیریتی پشتیبانی می‌کند:

| دستور | عملکرد |
|---|---|
| `exit` | خروج از برنامه |
| `reload` | بارگذاری مجدد فهرست تبلیغات و تحریم‌ها |
| `stats` | نمایش آمار درخواست‌های پردازش‌شده |
| `cache` | نمایش محتوای کش و TTL باقی‌مانده رکوردها |

### دستور reload

با اجرای این دستور، فایل‌های `ad_list.txt` و `sanction_list.txt` مجدداً خوانده می‌شوند و تغییرات جدید بدون نیاز به راه‌اندازی مجدد برنامه اعمال خواهند شد.

### دستور stats

این دستور آمار مربوط به درخواست‌های پردازش‌شده را نمایش می‌دهد.

### دستور cache

این دستور اطلاعات رکوردهای ذخیره‌شده در کش، شامل نام دامنه، IP و TTL باقی‌مانده را نمایش می‌دهد.

## ۹. قالب خروجی برنامه

برنامه برای هر درخواست، نتیجه را با پنج فیلد اصلی نمایش می‌دهد:

- Domain
- Source
- Status
- IP
- TTL

نمونه خروجی:

```text
Domain : example.com
Source : UPSTREAM
Status : OK
IP : 198.51.100.7
TTL : 5
```

### مقادیر Source

| مقدار | توضیحات |
|---|---|
| `AD_BLOCK` | دامنه در فهرست تبلیغات قرار دارد. |
| `SANCTION` | دامنه در فهرست تحریم‌ها قرار دارد. |
| `CACHE` | پاسخ از کش محلی دریافت شده است. |
| `UPSTREAM` | پاسخ از سرور بالادستی دریافت شده است. |
| `NONE` | ورودی نامعتبر بوده و درخواستی ارسال نشده است. |

### مقادیر Status

| مقدار | توضیحات |
|---|---|
| `OK` | درخواست با موفقیت پردازش شده است. |
| `NOT_FOUND` | دامنه در سرور Upstream پیدا نشده است. |
| `INVALID_INPUT` | ورودی واردشده نامعتبر است. |
| `SERVER_ERROR` | هنگام ارتباط با سرور یا دریافت پاسخ خطایی رخ داده است. |

## ۱۰. نحوه ارتباط با سرور Upstream

ارتباط بین برنامه اصلی و سرور Upstream با استفاده از پروتکل UDP انجام می‌شود.

در حالت شبیه‌سازی‌شده، برنامه اصلی نام دامنه را به‌صورت یک پیام متنی برای سرور Upstream ارسال می‌کند.

سرور پس از دریافت درخواست، دامنه را بررسی کرده و پاسخ مناسب را برمی‌گرداند.

قالب پاسخ موفق:

```text
OK,198.51.100.7,5
```

قالب پاسخ ناموفق:

```text
ERROR,DOMAIN_NOT_FOUND
```

در پاسخ موفق، اطلاعات زیر وجود دارند:

- وضعیت پاسخ
- نشانی IP دامنه
- مقدار TTL

در صورت عدم دریافت پاسخ در زمان تعیین‌شده، برنامه با استفاده از مکانیزم Timeout خطای ارتباطی را مدیریت می‌کند.

همچنین تعداد درخواست‌های دریافت‌شده توسط سرور Upstream با شمارنده `Request #N` مشخص می‌شود.

## ۱۱. سیستم کش محلی

برای کاهش تعداد درخواست‌های ارسالی به سرور Upstream و افزایش سرعت پاسخ‌گویی، یک سیستم کش محلی در پروژه پیاده‌سازی شده است.

در این سیستم، پاسخ‌های موفق مربوط به دامنه‌های عادی ذخیره می‌شوند.

هر رکورد کش شامل اطلاعات زیر است:

- نام دامنه
- نشانی IP
- مقدار اولیه TTL
- زمان ذخیره شدن رکورد

### نحوه عملکرد کش

۱. ابتدا بررسی می‌شود که دامنه در کش وجود دارد یا خیر.

۲. اگر رکورد معتبر باشد، پاسخ از کش دریافت می‌شود.

۳. TTL باقی‌مانده با توجه به زمان سپری‌شده محاسبه می‌شود.

۴. اگر TTL رکورد به پایان رسیده باشد، رکورد حذف شده و درخواست مجدداً به Upstream ارسال می‌شود.

۵. در صورت دریافت پاسخ موفق از Upstream، رکورد جدید در کش ذخیره می‌شود.

### فعال و غیرفعال کردن کش

برای فعال کردن کش:

```ini
cache_enabled=true
```

برای غیرفعال کردن کش:

```ini
cache_enabled=false
```

### محدودیت ظرفیت کش

با استفاده از پارامتر `cache_max_entries` می‌توان حداکثر تعداد رکوردهای کش را مشخص کرد.

در صورت پر شدن ظرفیت، قدیمی‌ترین رکورد حذف می‌شود تا فضای لازم برای ذخیره رکورد جدید فراهم شود.

## ۱۲. اتصال به DNS واقعی (قابلیت B6)

علاوه بر حالت شبیه‌سازی‌شده، پروژه از امکان اتصال به سرورهای واقعی DNS نیز پشتیبانی می‌کند.

برای فعال‌سازی این قابلیت، مقدار پارامتر زیر در فایل `config.txt` تغییر می‌کند:

```ini
real_dns_enabled=true
```

نشانی سرور DNS نیز از طریق پارامتر زیر تعیین می‌شود:

```ini
dns_server_ip=8.8.8.8
```

می‌توان از سرور عمومی دیگری مانند `1.1.1.1` نیز استفاده کرد.

در این حالت، برنامه با استفاده از کتابخانه `dnspython` درخواست DNS را به سرور تعیین‌شده ارسال کرده و پاسخ واقعی شامل IP و TTL را دریافت می‌کند.

برای بازگشت به حالت شبیه‌سازی‌شده:

```ini
real_dns_enabled=false
```

در حالت اجباری پروژه، ارتباط با Upstream شبیه‌سازی‌شده از طریق سوکت UDP خام و پیام‌های متنی انجام می‌شود و استفاده از کتابخانه آماده DNS فقط برای قابلیت امتیازی B6 مجاز است.

## ۱۳. ثبت گزارش درخواست‌ها (قابلیت B4)

برای ثبت اطلاعات درخواست‌های پردازش‌شده، قابلیت گزارش‌گیری در پروژه پیاده‌سازی شده است.

در صورت فعال بودن ثبت گزارش، اطلاعات درخواست‌ها در فایل `log.txt` ذخیره می‌شوند.

فعال‌سازی ثبت گزارش از طریق تنظیم زیر انجام می‌شود:

```ini
log_enabled=true
```

اطلاعات ثبت‌شده شامل موارد زیر است:

- زمان ثبت درخواست
- نام دامنه
- منبع پاسخ
- وضعیت درخواست
- نشانی IP
- مقدار TTL

نمونه‌ای از محتوای فایل گزارش:

```text
2026-10-25 14:30:01 | ads.example.com | AD_BLOCK | OK | 0.0.0.0 | 60
2026-10-25 14:30:04 | service.example.org | SANCTION | OK | 192.0.2.10 | 60
2026-10-25 14:30:08 | normal.example.net | UPSTREAM | OK | 198.51.100.7 | 5
```

## ۱۴. تست و ارزیابی پروژه

برای بررسی عملکرد صحیح برنامه، تست‌های بخش اصلی پروژه از T1 تا T13 در نظر گرفته شده‌اند.

این تست‌ها بخش‌های مختلف برنامه را پوشش می‌دهند.

| محدوده تست | موضوع بررسی |
|---|---|
| T1 تا T6 | دریافت ورودی، اعتبارسنجی، نرمال‌سازی، بررسی فهرست‌ها و اولویت‌بندی |
| T7 تا T9 | عملکرد کش، TTL و ارتباط با Upstream |
| T10 تا T13 | مدیریت خطاها، Timeout و رفتار برنامه در شرایط مختلف |

همچنین تست‌های مربوط به قابلیت‌های امتیازی شامل موارد زیر هستند:

- بررسی صحت آمار درخواست‌ها
- بررسی عملکرد دستور `reload`
- بررسی ثبت گزارش در `log.txt`
- بررسی نمایش اطلاعات کش
- بررسی محدودیت ظرفیت کش و حذف قدیمی‌ترین رکورد
- بررسی اتصال به DNS واقعی

برای اجرای تست‌های کش، دستور زیر قابل استفاده است:

```bash
python test_cache.py
```

خروجی‌های واقعی اجرای تست‌های T1 تا T13 در فایل `test_results.txt` ثبت شده‌اند.

## ۱۵. محدودیت‌های پیاده‌سازی

- ورودی نام دامنه از طریق کنسول دریافت می‌شود.
- ارتباط حالت شبیه‌سازی‌شده با Upstream از طریق UDP انجام می‌شود.
- سرور شبیه‌ساز از پاسخ‌های از پیش تعیین‌شده برای تست استفاده می‌کند.
- قابلیت DNS واقعی به نصب کتابخانه `dnspython` و دسترسی شبکه نیاز دارد.
- پاسخ‌های ذخیره‌شده در کش دارای زمان اعتبار مشخص هستند و پس از پایان TTL معتبر نخواهند بود.
- ظرفیت کش با پارامتر `cache_max_entries` قابل تنظیم است.
- عملکرد برنامه بر اساس مقادیر موجود در فایل `config.txt` تعیین می‌شود.

## ۱۶. تقسیم وظایف اعضای گروه

پیاده‌سازی پروژه به‌صورت گروهی انجام شده و مسئولیت بخش‌های مختلف میان سه عضو گروه تقسیم شده است.

### ۱۶-۱. متین علی نقیان

**مسئولیت‌ها:**

- پیاده‌سازی ورودی کنسول و دریافت نام دامنه از کاربر
- اعتبارسنجی ورودی و مدیریت ورودی‌های خالی یا نامعتبر
- نرمال‌سازی دامنه شامل تبدیل حروف به کوچک و حذف نقطه پایانی
- خواندن و بررسی فایل‌های `ad_list.txt` و `sanction_list.txt`
- پیاده‌سازی اولویت فهرست تبلیغات نسبت به فهرست تحریم‌ها
- برگرداندن خروجی با قالب دقیق Domain / Source / Status / IP / TTL
- پیاده‌سازی قابلیت امتیازی B2: دستور `reload` برای بارگذاری مجدد فهرست‌ها
- پیاده‌سازی قابلیت امتیازی B4: ثبت درخواست‌ها در فایل `log.txt`

**تست‌های مرتبط:**

تست‌های T1 تا T6 و تست‌های مربوط به قابلیت بارگذاری مجدد فهرست‌ها و گزارش‌گیری.

### ۱۶-۲. محمدرضا اکرمی

**مسئولیت‌ها:**

- ساخت برنامه جداگانه شبیه‌ساز سرور Upstream
- پیاده‌سازی ارتباط UDP بین Proxy و Upstream
- دریافت درخواست دامنه و برگرداندن IP و TTL
- پیاده‌سازی شمارنده درخواست‌ها با قالب `Request #N`
- مدیریت Timeout و پاسخ‌های خطا از سمت Upstream
- پیاده‌سازی قابلیت امتیازی B6: اتصال به DNS واقعی مانند `8.8.8.8` یا `1.1.1.1`
- مدیریت حالت DNS واقعی و شبیه‌سازی‌شده با استفاده از تنظیمات `config.txt`

**تست‌های مرتبط:**

تست‌های مربوط به ارتباط با Upstream، خطاهای شبکه و تست‌های T10 تا T13.

### ۱۶-۳. امیر محمد رضایی

**مسئولیت‌ها:**

- پیاده‌سازی سیستم کش محلی
- ذخیره IP و TTL دامنه‌های عادی
- محاسبه TTL باقی‌مانده با گذشت زمان
- حذف خودکار رکوردهای منقضی‌شده
- پشتیبانی از پارامتر `cache_enabled`
- پیاده‌سازی قابلیت امتیازی B1: دستور `stats` و نمایش آمار درخواست‌ها
- پیاده‌سازی قابلیت امتیازی B3: دستور `cache` و نمایش محتوای کش
- پیاده‌سازی قابلیت امتیازی B5: محدودیت ظرفیت کش با استفاده از `cache_max_entries` و حذف قدیمی‌ترین رکورد هنگام پر شدن ظرفیت

**تست‌های مرتبط:**

تست‌های T7 تا T9 و تست‌های مربوط به عملکرد کش و قابلیت‌های امتیازی آن.

## ۱۷. جمع‌بندی

در این پروژه یک پراکسی هوشمند DNS با زبان پایتون طراحی و پیاده‌سازی شده است که وظیفه دریافت و بررسی نام دامنه‌ها، شناسایی دامنه‌های تبلیغاتی و تحریم‌شده و ارسال درخواست دامنه‌های عادی به سرور Upstream را بر عهده دارد.

ارتباط میان برنامه اصلی و سرور Upstream از طریق پروتکل UDP انجام می‌شود. همچنین برای افزایش سرعت پاسخ‌گویی، سیستم کش محلی با قابلیت مدیریت TTL و محدودیت ظرفیت پیاده‌سازی شده است.

علاوه بر قابلیت‌های اصلی، امکانات امتیازی B1 تا B6 نیز در پروژه در نظر گرفته شده‌اند.

این پروژه با تقسیم مسئولیت میان سه عضو گروه توسعه داده شده است و فایل‌های تنظیمات، فهرست‌های نمونه، کدهای منبع، فایل تست و مستندات لازم برای اجرا و بررسی عملکرد آن ارائه شده‌اند.

تمام اعضای گروه با بخش مسئولیت خود و روند کلی عملکرد پروژه آشنایی دارند و می‌توانند منطق پیاده‌سازی را در جلسه ارائه توضیح دهند.
